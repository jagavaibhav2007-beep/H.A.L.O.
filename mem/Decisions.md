# Decisions
_Architectural, structural, and system design choices._

## Floating pill is the sole approval notification surface — 2026-08-09

**What:** removed per-approval Windows desktop toasts and the Tauri notification
plugin. Tier-3 work still pauses, while the always-on-top companion expands with
Approve, Deny, and Review controls.

**Why:** the toast duplicated the actionable floating pill and appeared as
repeated PowerShell notifications in development. One persistent approval
surface is clearer and cannot create notification spam.

**Tradeoff:** Halo no longer posts an Action Center entry for approvals. A
pending request remains checkpointed and visible when the companion reconnects.

## Managed commands share one contained Lane-1 executor — 2026-08-07

**What:** added model-visible `command_run` and `script_run` as durable
TaskRuntime tools, plus typed `dir_create`. Direct execution is argv-only and
generated Python/PowerShell is Tier 3. Approval binds the normalized request
and executable identity. Windows Job Objects own descendant cleanup; output is
bounded/redacted; declared artifacts, including PDFs, are verified separately
from exit status. The old `run_readonly_cmd` remains only as a schema-less
compatibility wrapper.

**Why:** terminal access is useful capability but not authority. A single
managed executor lets the Brain choose the cheapest capable route without
creating an open shell, a second permission system, or a subprocess path that
future Codex/Claude adapters could accidentally bypass.

**Ponytail boundary:** command spec, policy, redaction, process management, and
artifact checks deliberately live in one small module until independent reuse
or churn proves a split valuable. Security boundaries were not simplified:
unknowns fail Tier 3, opaque forms refuse, literal secrets fail before approval,
and Stop is tested against grandchildren.

**Hardening:** low-tier profiles belong only to the PATH-discovered executable,
not a same-name file. Windows creates the child suspended before Job assignment.
Task admission freezes both fingerprint and tier across queue waits. Custom
environments and all non-read-only Git operations are Tier 3; destructive Git
forms are marked destructive. Artifact hashing runs off the event loop, live
output and script scratch are capped, and obvious literal credentials fail
before approval. This is still same-user process containment, not an OS sandbox.

## Phase 3 UI foundation uses one compact rail and history-only terminal tasks — 2026-08-02
**Decision:** the existing workspace switches its 176px labelled sidebar to a 56px icon rail at `max-width: 640px`; it does not gain a second layout, collapse state, or another breakpoint. ## Phase-3a readiness (Tranche B) — two calls not to re-litigate — 2026-08-01
Context: closing PHASE3_READINESS_AUDIT.md's Tranche B (B3/B4/B5). Two decisions have non-obvious trade-offs a future session is likely to re-open:

**B3 — the checkpoint stays the sole source of truth for pending approvals; rehydrate is scoped by a narrowing SQL query, NOT by a persisted set in halo.db.** `rehydrate_pending` now selects only threads whose latest checkpoint carries an `__interrupt__` write (`graph._threads_with_open_interrupt`) instead of `aget_state`-ing every thread ever created. **Why not persist "threads with an open approval" to halo.db and skip the checkpoint scan entirely?** Because the approval is written into the LangGraph checkpoint by the graph invocation, and our own set would be a second write — a crash in the window between the two would silently lose an approval (no error, unresumable task). The whole point of rehydrate is to survive a crash, so a crash-lossy index defeats it. The SQL query is safe because `snap.interrupts` remains the authority that builds the payload: the query can only *narrow* which threads we deserialize, never fabricate or (verified empirically) miss one. **Also deliberately NOT done: deleting/archiving whole dormant threads' checkpoints.** No reliable "conversation is closed" signal exists, per-thread depth is already capped (`_CHECKPOINT_KEEP=20`), and the Brain is meant to own resumable history — archival would trade a real feature for disk that the depth cap already bounds. If checkpoints.db growth ever actually bites, revisit with an explicit user-driven "delete conversation" action, not a heuristic sweep.

**B5 — turns are capped (`MAX_TURNS=200`), but the activity store was deliberately left as an array copy, not rewritten to a mutable ring.** The audit's B5 asked for both a turn cap and an "index-based activity ring instead of full-array-copy per frame." The turn cap shipped. The ring rewrite did not, on purpose: B2 already moved the only high-rate activity producer (coding-agent stdout) to the separate, bounded `task_log`→`taskLogs` path, so `pushActivity`'s `[...activities, a]` copy is now human-paced and bounded at `ACTIVITY_CAP=10_000`. A mutable ring read through zustand/`useSyncExternalStore` would reintroduce exactly the `getSnapshot`-should-be-cached identity-bug class that blanked the whole app earlier in this same session (see Bugs.md 2026-08-01) — real risk for a copy cost that no longer has a high-rate trigger. Don't rewrite it unless a profiler shows activity frames arriving fast enough to matter *after* task_log already carries the streaming load.

## An answered approval card dismisses immediately — this is not a rule-3 exception — 2026-08-01
**Decision:** approve/deny/edit/stop remove the card from the store the instant the decision goes out on a live socket (`resolveApprovalLocally`), instead of waiting for the Brain's confirming frame to unmount it.

**Why it does not violate rule 3.** Rule 3 stops the UI claiming a *state change* the Brain hasn't confirmed — an unlocked Delete button implies a deletion that may not have happened. An approval card claims no state: it is a *question*. Once answered and sent, the question is genuinely answered, and what the tool actually did still arrives on the confirming frame and renders in the activity row. Every other rule-3 control (memory edit/delete, task pause/stop, skill toggle) keeps its unlock-on-confirm behaviour untouched. Read the ApprovalCard header comment ("resolves ONLY when the store removes it") with this entry next to it — the dismissal *is* the store removing it, just driven by the answer rather than the round-trip.

**The honesty gate, which is the load-bearing half.** Dismissal is conditional on `wsStatus === "connected"`. With the socket down, an `approval_response` only reaches the reconnect queue, and `dropStaleControlFrames` deliberately discards it if the Brain restarts on a fresh port — so dismissing there would tell the user they approved something the Brain never heard. In that case the card stays with its rule-3 spinner. Because the approval is durable and returns in the reconnect snapshot still pending, the card also unlocks on reconnect: still being mounted once connected is proof the answer never landed, and without the unlock it would sit on "Denying…" with no frame left that could ever clear it (the stuck-forever class in `mem/Bugs.md`).

**Trade-off accepted:** a tiny window where a card answered offline unlocks just as its queued decision lands, briefly offering a second answer. The Brain already dedups (`handle_approval_response`: first response for an `approval_id` wins), and a redundant answer is strictly better than an unanswerable card.

## Empty chat tabs are drafts; Recent starts at first submitted user message - 2026-07-27
**What:** the multi-chat registry distinguishes an untouched tab from a started conversation with a persisted `hasUserMessage` flag. Closing a tab with no submitted user message deletes it from the registry instead of retaining it in Recent; closing the last untouched tab creates one clean replacement. Any non-empty submitted message, including a short one like `hi`, flips the flag even if the title stays default.
**Why:** the earlier browser-tab-style model treated every closed tab as durable history, which polluted Recent with empty chats the user never actually used. The real product boundary is not "tab created" but "user asked something."
**Trade-off:** older stored records that predate the flag are treated as started during deserialization so existing short real conversations are preserved. This adds one more metadata field to the UI-only registry, but it keeps persistence semantics honest.

## Token-cost controls: Tracks A/B/C/D + gate of systemdesign/14 implemented - 2026-07-26
**What:** after a trivial "find a PDF, list latest downloads" task burned >150k tokens, implemented most of [systemdesign/14-token-economics.md](../systemdesign/14-token-economics.md). **Track A** (the dominant term): `dir_list`/`file_search` and `run_readonly_cmd`'s dir/ls path now go through one formatter (`_bounded_listing`) that returns flat text NEWEST-FIRST with mtime+size, a `limit` (default 50), and `os.scandir` that SKIPS entries whose `stat()` raises (OneDrive placeholders, `.crdownload`, races) instead of failing the call — so "which is latest" is answered by the ordering, no full read. Done and gate-green: **Track C** (real usage accumulation at the `llm._stream_once` choke point — already landed earlier this session); **gate.py** `_cap_result` (drop trailing list entries until the JSON fits instead of byte-slicing serialized JSON mid-token, which fed the model invalid JSON); **B5** (`memory._render_span` skips `role=="tool"` messages in the extraction/summary excerpt); **B1** (escalation decays — `_route_node` clears `escalated` after reading it, a one-shot); **B2** (`llm.is_transport_error` — escalate only on quality failures, never on TransportError/5xx/429); **B3** (soft cap keeps tool specs on the request and sends `tool_choice:"none"` instead of `tools=None`, preserving the cached prefix); **D1** (`turn_token_budget` setting, default 40k — cap CUMULATIVE input tokens per turn, reusing the existing soft-cap exit); **D2** (identical read-only-call suppression per turn, keyed on canonicalized args).
**Why:** `dir_list` returned name+is_dir with no mtime and in name order, so it structurally could not answer "which is newest" and the model read everything; `tool_specs()` re-shipped every round; the `escalated` flag was a permanent one-way latch; consolidation re-read the full unstubbed span; `_MAX_TOOL_ROUNDS` capped rounds, not cost.
**Correction to the doc:** doc 14's B1 *mechanism* ("add `escalated:False` to `run_turn`'s input dict") contradicts its own *intent* ("covers the next turn only") — the input dict is merged into checkpoint state BEFORE `_route_node` runs, so it would wipe escalation to zero turns. Implemented the intent via a one-shot read-then-clear in `_route_node`; the mechanism line in doc 14 should be corrected to match.
**Trade-off:** D1's ceiling and D2's suppression set live in the per-turn `_turn_ctx`, so both reset across a Tier-3 suspend/resume (fresh ctx) — acceptable, the incident was an uninterrupted read loop. Track A returns a str now, so `dir_list`/`file_search` no longer emit `list[dict]`/`list[str]` (gate `_cap_result`'s list-path no longer applies to them; their own `_LIST_TEXT_CAP` keeps output under the 8KB result cap). **C4** also landed: `spend_update` carries optional `session_tokens`/`last_turn_tokens` (three-file contract mirror), wired from `_bill_and_extract`/`snapshot`, projected in `reducer.ts` (`?? prior` so a snapshot without last_turn_tokens doesn't zero it), shown in Settings; `phase2_check` now asserts those fields flow through the real Brain. Doc 13's four stale claims corrected. **Remaining (both need a real OpenRouter key, so deferred to a human run):** B4 (volatile-content-last — only worth shipping if the real Gemma-4 route reports `cached_tokens > 0`), and the real-repro before/after that measures Track A's actual token delta. Green after all the above: 15 brain suites, `check_contract_sync`, phase2 E2E, `tsc`, contract + reducer selfchecks.

## Contract carries a version; the UI parser degrades instead of closing on skew - 2026-07-23
**What:** `hello`/`hello_ack` now carry `contract_version` (major.minor). The Brain closes with a terminal `incompatible_contract` error on a major mismatch. The UI's `parseIpcMessage` gained an opt-in tolerant mode used only by the live `onmessage` path: unknown frame types are logged and dropped (never `ws.close()`), unknown extra fields on a known type are ignored. Outbound validation and both selfchecks stay strict.
**Why:** before this, ANY schema skew — a new outbound type, an additive field — threw in `onmessage`, closed the socket, and the fixed 1s reconnect retried into the same throw forever: a silent infinite reconnect storm with no visible error. This will happen constantly during Phase 3 development, where the Brain restarts independently of a stale webview bundle (the stable launcher serves cached JS by design).
**Trade-off:** the UI now silently drops frames it doesn't understand instead of failing loud — acceptable because dropping beats an infinite reconnect loop, and a real incompatibility (major version mismatch) still surfaces as a persistent, honest "restart to update" state rather than being masked.

## Task runtime detaches long-running tasks from interactive chat turns - 2026-07-23 (implemented 2026-07-31)
**What:** a task-shaped tool records durable intent and task metadata, submits to a separate bounded `TaskRuntime`, and releases the interactive turn/conversation lock. `TaskContext` supplies cooperative cancel/pause, progress checkpoints, and coalesced `task_log`; completion re-enters the conversation as an untrusted internal continuation.
**Why:** long tools must not consume all interactive turn slots or violate the ≤2s halt rule. This is inherited by every Phase 3 sub-phase.
**Trade-off:** waiting/running/paused tasks survive as metadata but reconcile to a truthful failed state after restart; checkpointed partial effects can receive undo, but work is never blindly replayed. FIFO cap 2 remains; no priority/preemption until measured starvation justifies it.

## Memory v2: session-segment consolidation replaces per-turn extraction - 2026-07-23
**What:** redesigned the memory write path (systemdesign/03-memory.md v2, not yet implemented). Per-turn extraction is retired; a per-conversation `consolidation_cursor` plus four triggers (idle, shutdown, startup-recovery, token-pressure) drives ONE extraction pass per session segment, followed by a mem0-style per-candidate LLM decision (ADD/UPDATE/INVALIDATE/NOOP) against the top-5 vector neighbors. New episodic tier: one compact `session_summary` row per session (the user's proposal, adopted as a complementary layer). Beliefs gain Graphiti-style `valid_at`/`invalid_at`; snapshot hydration ships live rows only.
**Why:** measured 3 days of real use: one user statement had become ~8 near-duplicate rows, 60% of the table was dead yet fully replayed on every connect, and extraction cost O(N) LLM calls per session. Independent validation: mem0ai/mem0#4573 found 97.8% junk from exactly this per-turn permissive-extraction pattern (a stronger extraction model made it worse). Industry consensus (mem0, Letta sleep-time, LangMem background memory, Zep/Graphiti, Hindsight) is unanimous: extract in the background per segment, decide against neighbors instead of inserting unconditionally, and treat summaries as episodic complement — no surveyed system uses per-session summary blobs as primary memory (loses per-fact retrieval, per-fact provenance/rule-6 enforcement, and panel editability).
**Trade-off:** facts extracted at session end are not available for retrieval mid-session (working memory covers the live conversation, so this rarely matters); a hard crash consolidates late (startup-recovery) rather than never. The decision step adds 0–3 light calls per session — still ~10× cheaper than v1. Rollout M1–M4 in the design doc; provenance rule 6 stays enforced in store.py below the LLM decision layer.

## Real task controls fail honestly until Phase 3 provides a task runtime - 2026-07-22 (superseded 2026-07-31)
**What:** the real Phase-2 Brain responds to `task_op` and `lane_pin` with a correlated `operation_unsupported` error. The UI unlocks the exact pending control and shows the failure; it does not fabricate a local task transition.
**Why:** Phase 2 has durable task state but not the Phase-3 orchestration runtime needed to pause, resume, stop, reprioritize, or stream cooperative progress truthfully. Pretending success would make frontend state diverge from backend execution.
**Trade-off:** controls visible in the implemented shell can report unsupported in real mode until Phase 3. `dir_organize` remains bounded and off-loop, but live stepped progress/cooperative cancellation is deferred with the same boundary.

## Bound real-turn concurrency and evict idle conversation locks - 2026-07-22 (revised 2026-07-31)
**What:** the Brain admits at most four executing real turns, enforces hard global/per-principal request-admission caps before work queues, and serializes each conversation with a reference-counted lock lease that evicts idle entries.
**Why:** the earlier semaphore bounded execution but allowed an unbounded waiting-task/lock map under hostile loopback traffic. Admission must be bounded before allocation, and conversation IDs must not create permanent entries.
**Trade-off:** excess requests fail/reject instead of waiting indefinitely. The lock lease is more code than a plain dict, but is justified now that the trust-boundary review includes denial-of-service resistance.

## Operation errors use paired correlation fields in the shared contract - 2026-07-22
**What:** `error` frames may carry `operation_kind` and `operation_id`, but the pair is all-or-nothing and both mirrors reject malformed or extra fields.
**Why:** a generic conversation-level error cannot identify which Pause/Delete/Pin/etc. control should unlock, especially with multiple pending actions. Pairing avoids ambiguous partial correlation and lets reducers terminate only the matching operation.
**Trade-off:** the hand-mirrored schema and validators gained another invariant. `shared/check_contract_sync.py` compares complete schemas, and all contract self-checks must run after changes.

## Security-sensitive degraded logs expose exception class only - 2026-07-22
**What:** expected embedding fallback and secret/backend failure logs identify the exception class but omit exception text and local cache/credential details.
**Why:** exception strings from libraries can contain machine paths, backend metadata, or provider detail that is useful for local diagnosis but inappropriate in routine logs.
**Trade-off:** routine logs contain less diagnosis. Unexpected failures should be investigated through controlled local debugging, not by broadening default production log content.

## Multi-conversation chat: registry is UI-only state, persisted by ONE window — 2026-07-21
**What:** the chat panel became a browser-style tab strip. Each tab is one `conversation_id` = one LangGraph `thread_id`, so two tabs share no context (the user's actual complaint: unrelated questions polluting each other's context). Backend needed no change — the whole blocker was `useHaloConnection`'s hardcoded `conversationIdRef`. The registry (`{all, open, activeId}`) lives in `state/conversations.ts` as pure functions with `conversations.selfcheck.ts`, held and persisted by `store.ts`, mirroring the existing `reducer.ts`/`store.ts` split.
**Why UI-only:** no frame tells us what the tab strip should look like — it's the same reasoning that keeps `activeView` out of the pure reducer. `reducer.ts` was already keyed per conversation and needed no edit at all.
**Two webviews, one localStorage key:** the orb and workspace boot separate store instances with no shared JS heap, so both writing `halo.conversations.v1` would let a stale copy clobber a fresh one. Resolved by making the workspace the *only* writer: it alone has chat UI, so it alone calls the mutating actions, and those are the only functions that persist. `markUnread` runs in both windows (off `applyFrame`) and deliberately does **not** persist — `unread` is per-session by definition. Don't add a persisting action that both windows can reach without revisiting this.
**Contract:** one optional `approval_request.conversation_id` (D2's "a real gap is a doc conversation, not a quiet field addition" — hence the `systemdesign/11-ipc-contract.md` prose). Approve/deny resolve by `approval_id`, but the card's "Stop this task" sends `interrupt`, which **is** keyed by conversation — without it a card raised by a background thread would interrupt whichever thread was on screen. Note `check_contract_sync.py` only compares `required` lists, so optional fields are invisible to it; `test_gate` check 7 carries the emission assertion instead.
**Honest restart state:** the Brain keeps history (checkpoints keyed by `conversation_id`) but `snapshot()` replays tasks/approvals/beliefs/activity — never turns. So a reopened tab after a restart is genuinely blank, and the empty state says so ("Earlier messages in this thread are on the Brain") rather than looking like data loss. Under `--mock` there are no checkpoints at all, so that copy is optimistic in mock mode only.

## Phase 2 architecture decisions (D1-D9) — 2026-07-21
Compact record of `phase-2-plan.md`'s original "Architecture decisions" section (that doc was retired 2026-08-01 once Phase 2 shipped; this list is now the durable record — see git history for the doc's original framing).
- **D1 — real Brain is a third handler behind the same server, not a new server.** `server.py` keeps auth/lock/envelope/lock-per-conversation/routing untouched; default dispatch becomes the real graph, `--mock` unchanged. *Why:* the mock stays as the UI's permanent test harness and living contract doc — replacing it would lose that.
- **D2 — contract frozen for the whole phase.** No new message types/fields; a real gap is a systemdesign-doc conversation, never a quiet field addition. *Why:* Phase 1's payoff (mock-proven shapes) only holds if the real Brain emits exactly what the UI already renders. Verified continuously via `check_contract_sync.py` (still 25 types, zero drift).
- **D3 — one store module owns SQLite; LangGraph checkpoints get their own file.** `store.py` is the sole writer of `halo.db` (beliefs/actions/tasks/spend/settings); `checkpoints.db` is separate. *Why:* a corrupt/wiped checkpoint store can never take beliefs down with it; the store is the "one choke point for memory writes."
- **D4 — the gate is a wrapper around tool execution, not a per-tool branch.** One `classify()` pure function + one `gated_execute()` every tool call passes through; a tool absent from the registry is Tier 3 by construction. *Why:* per-tool scattered checks are exactly what "one enforcement point" forbids — see Patterns.md's gate/registry entry.
- **D5 — routing is rule-based, not model-based.** Cheap signals (code fences/stack traces, planning verbs + multi-step shape, length, explicit ask, sticky post-failure escalation) pick light/heavy; no LLM call decides. *Why:* keeps routing inspectable (logged to activity) and removes an extra paid call just to pick a model.
- **D6 — checkpoint intent-before/result-after; reconcile on resume.** A dead mid-tool turn re-enters at the intent record and reconciles (does the file exist / did the move happen?) before deciding to re-run or skip. *Why:* makes "kill mid-task -> resume" honest instead of "re-run and hope."
- **D7 — undo is an inverse recorded at execution time, executed later.** Each undoable action's row carries its inverse (built from the actual result, e.g. actual suffixed path on a collision) plus a precondition (path/sha256); `undo` re-checks the precondition, consumes the token atomically, then runs the inverse through the SAME gate execution tail (Tier 2, trusted — re-classifying would let arg shapes demote tiers or block honest reversals of approved Tier-3 actions). *Why:* a fake/best-effort undo is worse than an honest `undoable:false`.
- **D8 — secrets live in Windows Credential Manager via `keyring`; the key never crosses the IPC boundary.** Only status (`set`/`missing`) ever leaves the Brain; no key → chat returns a plain `error` naming Settings, not a crash. *Why:* per cross-cutting rule 4, the key string must exist at exactly one call site (the OpenRouter header) — never in frames, logs, DB, or exceptions.
- **D9 — new dependencies, each ponytail-gated.** Added: `langgraph`+`langgraph-checkpoint-sqlite` (resumable/interruptible graph state — hand-rolling this is the over-engineering trap), `httpx` (async streaming; blocking `requests` would stall every conversation), `sqlite-vec`+`fastembed` (belief similarity, no cloud embeddings), `keyring`. Deliberately NOT added: an ORM (5-table raw SQL), a migration framework (versioned `schema_version` pragma + idempotent DDL), LangChain beyond LangGraph's core, a scheduler lib (decay is a start-time check + daily `asyncio.sleep`).

## Vitest introduced (scoped) for the two React hooks selfchecks can't reach - 2026-07-18
**What:** added `vitest` + `@testing-library/react` + `jsdom` as UI devDeps and a `test` block in `ui/vite.config.ts` (reusing the existing Vite/React pipeline), plus `npm test` → `vitest run`. Scoped to `ui/src/**/*.test.tsx`: exactly two files — `usePendingConfirm.test.tsx` (rule-3 lock/unlock/dedup) and `usePeekSource.test.tsx` (peek most-recent-wins + narrate filter, driven through the real store via `applyFrame`).
**Why:** these are React hooks — the plain `*.selfcheck.ts` idiom (a pure function replaying canned input) can't render them, and every other UI module with pure logic is already covered by a selfcheck. ## Document ingestion: extract-then-digest, no heavy deps — 2026-07-24
**What:** designed [systemdesign/13-document-ingestion.md](../systemdesign/13-document-ingestion.md) (+ techstack/13) after a live test showed 8 markdown files burning ~68k tokens and escalating to the HEAVY model. Three layers: (0) deterministic `extract.py` (extension→markdown dispatcher: pypdfium2/pypdf for PDF, mammoth DOCX, openpyxl XLSX, markdownify HTML) plus `file_read` cap 64KB→8KB with offset/limit paging; (1) projection-time eviction in `_prompt_messages` — tool results older than the current round become stable restorable stubs (file is still on disk = the reference); (2) `doc_digest` map-reduce tool — one LIGHT call per doc returning a fixed JSON digest, one reduce, only ~1–2k tokens ever enter chat history; digests cached by (path, sha256).
**Why:** the burn was verified quadratic — the tool loop re-sends full history every round, so each 64KB read is retransmitted on every later round; LIGHT failures on oversized prompts then escalate the bloated history to HEAVY. Researched via subagents against markitdown, docling, pymupdf4llm, unstructured, kreuzberg, OpenHands condenser, Anthropic context-editing/programmatic-tool-calling, Aider repo-map, LangGraph map-reduce, LlamaIndex DocumentSummaryIndex, LLMLingua; provenance table in the design doc.

Layer-1 stubbing costs an occasional re-read round-trip when the model genuinely needs old content back — lossless because pagination exists. New deps are only mammoth/openpyxl/markdownify (pure Python, few MB).

## Checkpoint pruning is timing-gated, not interrupt-filtered — 2026-07-29
**What:** `graph.py._prune_checkpoints` (newest 20/thread) is only ever called from `_finish_turn`'s `error/done` branch — never from the `return True` branch that fires when the turn suspended on a Tier-3 `interrupt()`.

**Trade-off:** the invariant lives in *when* `_prune_checkpoints` is called, not in the function itself — a future caller that invokes it from anywhere else (e.g. a periodic sweep) must re-derive this safety argument or risk deleting a live suspended thread's resume state. ## `snapshot_complete` is the sole authoritative snapshot terminator — 2026-07-29 (revised 2026-07-31)

**Why:** spend can arrive during normal operation and therefore cannot safely double as a transaction boundary. Connection authentication synchronously starts a fresh snapshot epoch, and the explicit marker closes it.

## Orb-window `conversations` map is LRU-capped at 2x the workspace registry — 2026-07-29
