# Decisions
_Architectural, structural, and system design choices._

## Token-cost controls: Tracks A/B/C/D + gate of systemdesign/14 implemented - 2026-07-26
**What:** after a trivial "find a PDF, list latest downloads" task burned >150k tokens, implemented most of [systemdesign/14-token-economics.md](../systemdesign/14-token-economics.md). **Track A** (the dominant term): `dir_list`/`file_search` and `run_readonly_cmd`'s dir/ls path now go through one formatter (`_bounded_listing`) that returns flat text NEWEST-FIRST with mtime+size, a `limit` (default 50), and `os.scandir` that SKIPS entries whose `stat()` raises (OneDrive placeholders, `.crdownload`, races) instead of failing the call — so "which is latest" is answered by the ordering, no full read. Done and gate-green: **Track C** (real usage accumulation at the `llm._stream_once` choke point — already landed earlier this session); **gate.py** `_cap_result` (drop trailing list entries until the JSON fits instead of byte-slicing serialized JSON mid-token, which fed the model invalid JSON); **B5** (`memory._render_span` skips `role=="tool"` messages in the extraction/summary excerpt); **B1** (escalation decays — `_route_node` clears `escalated` after reading it, a one-shot); **B2** (`llm.is_transport_error` — escalate only on quality failures, never on TransportError/5xx/429); **B3** (soft cap keeps tool specs on the request and sends `tool_choice:"none"` instead of `tools=None`, preserving the cached prefix); **D1** (`turn_token_budget` setting, default 40k — cap CUMULATIVE input tokens per turn, reusing the existing soft-cap exit); **D2** (identical read-only-call suppression per turn, keyed on canonicalized args).
**Why:** `dir_list` returned name+is_dir with no mtime and in name order, so it structurally could not answer "which is newest" and the model read everything; `tool_specs()` re-shipped every round; the `escalated` flag was a permanent one-way latch; consolidation re-read the full unstubbed span; `_MAX_TOOL_ROUNDS` capped rounds, not cost.
**Correction to the doc:** doc 14's B1 *mechanism* ("add `escalated:False` to `run_turn`'s input dict") contradicts its own *intent* ("covers the next turn only") — the input dict is merged into checkpoint state BEFORE `_route_node` runs, so it would wipe escalation to zero turns. Implemented the intent via a one-shot read-then-clear in `_route_node`; the mechanism line in doc 14 should be corrected to match.
**Trade-off:** D1's ceiling and D2's suppression set live in the per-turn `_turn_ctx`, so both reset across a Tier-3 suspend/resume (fresh ctx) — acceptable, the incident was an uninterrupted read loop. Track A returns a str now, so `dir_list`/`file_search` no longer emit `list[dict]`/`list[str]` (gate `_cap_result`'s list-path no longer applies to them; their own `_LIST_TEXT_CAP` keeps output under the 8KB result cap). **C4** also landed: `spend_update` carries optional `session_tokens`/`last_turn_tokens` (three-file contract mirror), wired from `_bill_and_extract`/`snapshot`, projected in `reducer.ts` (`?? prior` so a snapshot without last_turn_tokens doesn't zero it), shown in Settings; `phase2_check` now asserts those fields flow through the real Brain. Doc 13's four stale claims corrected. **Remaining (both need a real OpenRouter key, so deferred to a human run):** B4 (volatile-content-last — only worth shipping if the real Gemma-4 route reports `cached_tokens > 0`), and the real-repro before/after that measures Track A's actual token delta. Green after all the above: 15 brain suites, `check_contract_sync`, phase2 E2E, `tsc`, contract + reducer selfchecks.

## Contract carries a version; the UI parser degrades instead of closing on skew - 2026-07-23
**What:** `hello`/`hello_ack` now carry `contract_version` (major.minor). The Brain closes with a terminal `incompatible_contract` error on a major mismatch. The UI's `parseIpcMessage` gained an opt-in tolerant mode used only by the live `onmessage` path: unknown frame types are logged and dropped (never `ws.close()`), unknown extra fields on a known type are ignored. Outbound validation and both selfchecks stay strict.
**Why:** before this, ANY schema skew — a new outbound type, an additive field — threw in `onmessage`, closed the socket, and the fixed 1s reconnect retried into the same throw forever: a silent infinite reconnect storm with no visible error. This will happen constantly during Phase 3 development, where the Brain restarts independently of a stale webview bundle (the stable launcher serves cached JS by design).
**Trade-off:** the UI now silently drops frames it doesn't understand instead of failing loud — acceptable because dropping beats an infinite reconnect loop, and a real incompatibility (major version mismatch) still surfaces as a persistent, honest "restart to update" state rather than being masked.

## Task runtime detaches long-running tasks from interactive chat turns - 2026-07-23 (design, systemdesign/12-task-runtime.md)
**What:** a task-shaped tool (coding-agent run, browser playbook, `dir_organize`) will not execute inline inside a turn. It records an intent row, submits to a separate bounded `TaskRuntime` (own worker cap, independent of the 4-slot turn semaphore), and the turn returns immediately. A `TaskContext` gives tools cooperative cancel/pause plus a new coalesced `task_log` frame; completion re-enters the conversation as a normal follow-up turn; crash recovery reconciles the intent row before ever resuming (never blindly re-runs a non-idempotent side effect).
**Why:** today a long tool call IS a turn — it holds one of 4 global turn slots and the conversation lock for its whole duration, with cancellation only checked between LLM stream deltas (never mid-tool). Four long Phase 3 tasks would hang every new conversation in the app with no error, and "stop" would violate the contract's own ≤2s halt rule. This is the single highest-leverage fix because every Phase 3 sub-phase (3a-3e) inherits whatever shape this takes.
**Trade-off:** no task persistence beyond the intent/result activity rows (a queued-but-unstarted task doesn't survive a Brain restart — acceptable since it never had side effects yet); FIFO with a cap of 2 workers, no priority/preemption until a real starvation case appears. Design only as of 2026-07-23 — implementation (B2) is the gate before Phase 3a can start.

## Memory v2: session-segment consolidation replaces per-turn extraction - 2026-07-23
**What:** redesigned the memory write path (systemdesign/03-memory.md v2, not yet implemented). Per-turn extraction is retired; a per-conversation `consolidation_cursor` plus four triggers (idle, shutdown, startup-recovery, token-pressure) drives ONE extraction pass per session segment, followed by a mem0-style per-candidate LLM decision (ADD/UPDATE/INVALIDATE/NOOP) against the top-5 vector neighbors. New episodic tier: one compact `session_summary` row per session (the user's proposal, adopted as a complementary layer). Beliefs gain Graphiti-style `valid_at`/`invalid_at`; snapshot hydration ships live rows only.
**Why:** measured 3 days of real use: one user statement had become ~8 near-duplicate rows, 60% of the table was dead yet fully replayed on every connect, and extraction cost O(N) LLM calls per session. Independent validation: mem0ai/mem0#4573 found 97.8% junk from exactly this per-turn permissive-extraction pattern (a stronger extraction model made it worse). Industry consensus (mem0, Letta sleep-time, LangMem background memory, Zep/Graphiti, Hindsight) is unanimous: extract in the background per segment, decide against neighbors instead of inserting unconditionally, and treat summaries as episodic complement — no surveyed system uses per-session summary blobs as primary memory (loses per-fact retrieval, per-fact provenance/rule-6 enforcement, and panel editability).
**Trade-off:** facts extracted at session end are not available for retrieval mid-session (working memory covers the live conversation, so this rarely matters); a hard crash consolidates late (startup-recovery) rather than never. The decision step adds 0–3 light calls per session — still ~10× cheaper than v1. Rollout M1–M4 in the design doc; provenance rule 6 stays enforced in store.py below the LLM decision layer.

## Real task controls fail honestly until Phase 3 provides a task runtime - 2026-07-22
**What:** the real Phase-2 Brain responds to `task_op` and `lane_pin` with a correlated `operation_unsupported` error. The UI unlocks the exact pending control and shows the failure; it does not fabricate a local task transition.
**Why:** Phase 2 has durable task state but not the Phase-3 orchestration runtime needed to pause, resume, stop, reprioritize, or stream cooperative progress truthfully. Pretending success would make frontend state diverge from backend execution.
**Trade-off:** controls visible in the implemented shell can report unsupported in real mode until Phase 3. `dir_organize` remains bounded and off-loop, but live stepped progress/cooperative cancellation is deferred with the same boundary.

## Bound real-turn concurrency; keep the conversation-lock map plain - 2026-07-22 (revised 2026-07-23)
**What:** the Brain admits at most four concurrent real turns globally via a semaphore, and serializes per-conversation with a plain `dict[str, asyncio.Lock]`.
**Why:** unlimited model/tool turns can exhaust local/provider resources — the semaphore is a cheap, real bound worth keeping. The reference-counted lease design (2026-07-22) that garbage-collected idle lock entries was reverted on 2026-07-23: 68 lines to reclaim ~KB of locks in a single-user desktop app was over-engineering (ponytail-review). The dict grows one lock per conversation_id and is never reclaimed — negligible for a local companion.
**Trade-off:** a fifth independent conversation waits for capacity. Four is a conservative local-desktop default, not an adaptive target; change it only with measured evidence. The lock map is unbounded in theory (`ponytail:` marked in `server.py`); add GC only if a session ever spans thousands of conversations.

## Operation errors use paired correlation fields in the shared contract - 2026-07-22
**What:** `error` frames may carry `operation_kind` and `operation_id`, but the pair is all-or-nothing and both mirrors reject malformed or extra fields.
**Why:** a generic conversation-level error cannot identify which Pause/Delete/Pin/etc. control should unlock, especially with multiple pending actions. Pairing avoids ambiguous partial correlation and lets reducers terminate only the matching operation.
**Trade-off:** the hand-mirrored schema and validators gained another invariant. `shared/check_contract_sync.py` compares complete schemas, and all contract self-checks must run after changes.

## Security-sensitive degraded logs expose exception class only - 2026-07-22
**What:** expected embedding fallback and secret/backend failure logs identify the exception class but omit exception text and local cache/credential details.
**Why:** exception strings from libraries can contain machine paths, backend metadata, or provider detail that is useful for local diagnosis but inappropriate in routine logs.
**Trade-off:** routine logs contain less diagnosis. Unexpected failures should be investigated through controlled local debugging, not by broadening default production log content.

## Multi-conversation chat: registry is UI-only state, persisted by ONE window — 2026-07-21
**What:** the chat panel became a browser-style tab strip. Each tab is one `conversation_id` = one LangGraph `thread_id`, so two tabs share no context (the user's actual complaint: unrelated questions polluting each other's context). Backend needed no change — the whole blocker was `useHaloConnection`'s hardcoded `conversationIdRef`. The registry (`{all, open, activeId}`) lives in `state/conversations.ts` as pure functions with `conversations.selfcheck.ts`, held and persisted by `store.ts`, mirroring the existing `reducer.ts`/`store.ts` split.
**Why UI-only:** no frame tells us what the tab strip should look like — it's the same reasoning that keeps `activeView` out of the pure reducer. `reducer.ts` was already keyed per conversation and needed no edit at all.
**Two webviews, one localStorage key:** the orb and workspace boot separate store instances with no shared JS heap, so both writing `halo.conversations.v1` would let a stale copy clobber a fresh one. Resolved by making the workspace the *only* writer: it alone has chat UI, so it alone calls the mutating actions, and those are the only functions that persist. `markUnread` runs in both windows (off `applyFrame`) and deliberately does **not** persist — `unread` is per-session by definition. Don't add a persisting action that both windows can reach without revisiting this.
**Contract:** one optional `approval_request.conversation_id` (D2's "a real gap is a doc conversation, not a quiet field addition" — hence the `systemdesign/11-ipc-contract.md` prose). Approve/deny resolve by `approval_id`, but the card's "Stop this task" sends `interrupt`, which **is** keyed by conversation — without it a card raised by a background thread would interrupt whichever thread was on screen. Note `check_contract_sync.py` only compares `required` lists, so optional fields are invisible to it; `test_gate` check 7 carries the emission assertion instead.
**Honest restart state:** the Brain keeps history (checkpoints keyed by `conversation_id`) but `snapshot()` replays tasks/approvals/beliefs/activity — never turns. So a reopened tab after a restart is genuinely blank, and the empty state says so ("Earlier messages in this thread are on the Brain") rather than looking like data loss. Under `--mock` there are no checkpoints at all, so that copy is optimistic in mock mode only.

## Phase 2 architecture decisions (D1-D9) — 2026-07-21
Compact record of phase-2-plan.md's "Architecture decisions" section; see that doc for full detail.
- **D1 — real Brain is a third handler behind the same server, not a new server.** `server.py` keeps auth/lock/envelope/lock-per-conversation/routing untouched; default dispatch becomes the real graph, `--mock` unchanged. *Why:* the mock stays as the UI's permanent test harness and living contract doc — replacing it would lose that.
- **D2 — contract frozen for the whole phase.** No new message types/fields; a real gap is a systemdesign-doc conversation, never a quiet field addition. *Why:* Phase 1's payoff (mock-proven shapes) only holds if the real Brain emits exactly what the UI already renders. Verified continuously via `check_contract_sync.py` (still 25 types, zero drift).
- **D3 — one store module owns SQLite; LangGraph checkpoints get their own file.** `store.py` is the sole writer of `halo.db` (beliefs/actions/tasks/spend/settings); `checkpoints.db` is separate. *Why:* a corrupt/wiped checkpoint store can never take beliefs down with it; the store is the "one choke point for memory writes."
- **D4 — the gate is a wrapper around tool execution, not a per-tool branch.** One `classify()` pure function + one `gated_execute()` every tool call passes through; a tool absent from the registry is Tier 3 by construction. *Why:* per-tool scattered checks are exactly what "one enforcement point" forbids — see Patterns.md's gate/registry entry.
- **D5 — routing is rule-based, not model-based.** Cheap signals (code fences/stack traces, planning verbs + multi-step shape, length, explicit ask, sticky post-failure escalation) pick light/heavy; no LLM call decides. *Why:* keeps routing inspectable (logged to activity) and removes an extra paid call just to pick a model.
- **D6 — checkpoint intent-before/result-after; reconcile on resume.** A dead mid-tool turn re-enters at the intent record and reconciles (does the file exist / did the move happen?) before deciding to re-run or skip. *Why:* makes "kill mid-task -> resume" honest instead of "re-run and hope."
- **D7 — undo is an inverse recorded at execution time, executed later.** Each undoable action's row carries its inverse (built from the actual result, e.g. actual suffixed path on a collision) plus a precondition (path/sha256); `undo` re-checks the precondition, consumes the token atomically, then runs the inverse through the SAME gate execution tail (Tier 2, trusted — re-classifying would let arg shapes demote tiers or block honest reversals of approved Tier-3 actions). *Why:* a fake/best-effort undo is worse than an honest `undoable:false`.
- **D8 — secrets live in Windows Credential Manager via `keyring`; the key never crosses the IPC boundary.** Only status (`set`/`missing`) ever leaves the Brain; no key → chat returns a plain `error` naming Settings, not a crash. *Why:* per cross-cutting rule 4, the key string must exist at exactly one call site (the OpenRouter header) — never in frames, logs, DB, or exceptions.
- **D9 — new dependencies, each ponytail-gated.** Added: `langgraph`+`langgraph-checkpoint-sqlite` (resumable/interruptible graph state — hand-rolling this is the over-engineering trap), `httpx` (async streaming; blocking `requests` would stall every conversation), `sqlite-vec`+`fastembed` (belief similarity, no cloud embeddings), `keyring`. Deliberately NOT added: an ORM (5-table raw SQL), a migration framework (versioned `schema_version` pragma + idempotent DDL), LangChain beyond LangGraph's core, a scheduler lib (decay is a start-time check + daily `asyncio.sleep`).

## Stable attached launcher by default; hot reload is opt-in - 2026-07-17
**What:** `./dev.ps1` runs the UI in its own terminal instead of spawning a detached PowerShell. Its default stable path uses `ui/src-tauri/tauri.stable.conf.json`, `npm run dev:stable`, `vite preview`, and Tauri `--no-watch`; `-WatchNative` selects the original Vite dev server and native watcher. A named mutex rejects a second launcher before it starts any build or server.
**Why:** automated workspace synchronization emits metadata-only writes across the dirty tree, which made both watchers repeatedly reload otherwise unchanged code. An attached process also gives Ctrl+C one ownership path for Tauri, Brain, Voice, and the frontend server.
**Trade-off:** stable mode performs a frontend build at startup and does not live-reload edits. Developers intentionally editing UI/Rust can pass `-WatchNative`; agent-driven runs favor continuity and trustworthy logs.

## Clip the Windows capsule at the HWND layer - 2026-07-17
**What:** the orb/capsule window uses a target-specific Win32 GDI dependency and `SetWindowRgn` to make the native window itself a 360x52 pill. Tauri's transparent background remains enabled, with an explicit zero-alpha `backgroundColor`.
**Why:** the existing CSS radius correctly shaped the DOM but could not alter the rectangular native window or its hit-test region. A native region is the smallest Windows-specific fix that makes painting and pointer bounds agree with the visual capsule.
**Trade-off:** a small platform-specific unsafe block and one Windows-only crate feature. Non-Windows builds keep a no-op shaping function; resize and DPI events reapply the region so physical dimensions stay correct.

**What:** removed the unused Vite, React, and Tauri placeholder SVG/PNG assets, removed the Vite favicon reference, and dropped stale `peek`/resize-drag capability entries left after the capsule redesign. The bundle icons still referenced by `tauri.conf.json` remain.

## Approval card: `interrupt` lives on the card as "Stop this task" — 2026-07-13
**What:** Step 10's `ApprovalCard` has a "Stop this task" link that sends `interrupt(conversation_id)`, kept in the Step-10 file rather than the chat/status-strip. It is deliberately distinct from Deny: Deny answers *this one action* (`approval_response{deny}` → the task pauses gracefully), while Stop cancels *the whole conversation's pending work* (implicit deny + pause).
**Why:** the "stale-card rule" (interrupt removes a pending card) is a Step-10 acceptance item, but nothing in the UI could send `interrupt` — the outbound union was `UserMsg|TaskOpMsg|UndoMsg`. `task_op` is not a substitute: `handle_task_op` only broadcasts a `task_state` and never resolves the mock's pending-approval future, and it defaults `task_id` to the seed. A real `sendInterrupt` was needed regardless; putting the affordance on the card makes the rule clickable/verifiable without touching Step-6/8 components. The card's *removal* was already automatic — the store's `resolveApprovalsForTask` fires on the `task_state:paused` that `handle_interrupt` broadcasts.
**Trade-off:** a 4th control on the most trust-critical surface. Acceptable because it's visually secondary (a small underlined link in the footer, not a button) and semantically separate from the Approve/Deny/Edit row. **A broader chat/global "Stop" is the eventual home** (Step 8/11) — when that lands, the card link can defer to it.
**Also settled:** `approval_response.reply_to` MUST be the request's `approval_id`, never the envelope `id` — the Brain keys `_pending_approvals` by `approval_id`, so the envelope id would leave the future unresolved forever (the standing envelope-id-collision trap).

## User messages live in the store as turns, appended at send time — 2026-07-12
**What:** Step 8's chat renders one ordered `turns` array per conversation, a `UserTurn | AssistantTurn` union discriminated by `role`. Assistant turns come from `token`/`done` frames (as before); user turns are appended by a pure `appendUserTurn(state, convId, text, id)` helper (wrapped in the store), called from `ChatView` right before `sendUserMsg`.
**Why:** `user_msg` is never echoed back — not by the mock, and not by Phase 2's real Brain (the reducer already noted "the user_msg echo may be local-only"). Merging a local user-message list with store assistant turns in the component fails on the cases that actually occur (two sends before a reply, an error/interrupted turn with no paired assistant turn, tokens for an unknown conversation_id). One ordered list appended in arrival order is the honest D7 model.
**Why not in `useHaloConnection`:** that hook is transport-only by design (no business logic in the UI WS client). The view owning "reflect my own send" keeps that boundary intact. The user turn's `id` is just a React key — it needn't match the sent frame's id, so there's no correlation risk.
**Trade-off:** `turns` became a union, so every `.status/.taskId/.note` access needs `role === "assistant"` narrowing (reducer callbacks + a `assistantTurn()` assert-helper in the selfcheck). ~15 min of narrowing, not a rewrite. Selfcheck scenario 7 pins the one behavior the union could silently regress (user turn → next token opens a fresh assistant turn, not a fold-in).

## Three-process architecture — 2026-07-10
**What:** Tauri (Rust) UI is the parent process; it spawns Brain (Python/LangGraph) and Voice (Python/Pipecat) as child processes, all talking over an authenticated local-loopback WebSocket.
**Why:** matches Halo-PRD.md's process model; keeps the permission gate meaningful by putting a real auth choke point (hello-token handshake) on the only transport between processes.
**Trade-off:** more moving parts to supervise (backoff/restart logic) than a single-process app.

## Sidecars run from source in dev; packaging deferred — 2026-07-10
**What:** Phase 0 spawns `python -m brain`/`python -m voice` directly rather than packaging them as PyInstaller binaries.
**Why:** packaging is explicitly out of scope for Phase 0 (walking-skeleton phase); avoids building binary packaging before the process contract is even proven.
**Trade-off:** dev-mode cwd resolution (`CARGO_MANIFEST_DIR` → repo root) is a `// ponytail:`-marked stopgap that the packaged-binary phase will replace.

## std::process::Command over tauri-plugin-shell sidecar API — 2026-07-10
**What:** Step 6's Rust supervisor uses plain `std::process::Command` instead of Tauri's `externalBin`/sidecar plugin machinery.
**Why:** that plugin API is built for packaged binaries; since packaging is deferred, it's the wrong rung on the ladder for dev-mode `python -m brain`.

## Tauri→React state events are webview events, not IPC frames — 2026-07-10
**What:** the `sidecar-state` event (`{process, state}`) that Step 6 emits to React uses `tauri::Emitter::emit`, and is NOT added to `shared/ipc-contract.json`.
**Why:** it's a Tauri-internal signal about OS process health, distinct from the Brain↔UI/Voice WebSocket message contract — conflating the two would blur "can I chat" (WS state) with "is the Brain process alive" (sidecar state), which are genuinely different things (Step 7 keeps them as two separate pieces of UI state).

## Explicit authentication acknowledgement — 2026-07-10
**What:** Brain sends the transport-level `hello_ack` frame after validating `hello`; UI and Voice do not send application messages before receiving it.
**Why:** an open socket does not prove that a session token was accepted, so optimistic queue flushing could lose messages during a restart race.
**Trade-off:** adds one IPC message and one handshake step, but gives clients an unambiguous authenticated state.

## Crash-safe single-Brain lock — 2026-07-10
**What:** Brain holds an OS file lock on `%LOCALAPPDATA%\Halo\brain.lock` for its process lifetime.
**Why:** prevents manually launched or duplicated Brain processes from racing to own `session.json`; OS locks release automatically after crashes so Tauri can restart Brain.
**Trade-off:** a second Brain exits immediately instead of running independently under the same OS account.

## Panel data as snapshot-on-connect + delta-on-change — 2026-07-11
**What:** Memory and Skills panels are fed by outbound `belief_state`/`skill_state` frames (Phase 1 Step 1), pushed as a full snapshot after `hello_ack` and again as single deltas when one item changes — the same pattern `task_state` already uses. The UI stores them as idempotent upserts keyed by `belief_id`/`skill_name`.
**Why:** a reconnecting or second client (orb + workspace both connect) must be able to rebuild full panel state from the event stream alone, with no separate query API; id-keyed upserts make snapshot re-pushes converge instead of duplicating.
**Trade-off:** the Brain re-sends all beliefs/skills on every connect (fine at Halo's single-user scale; a paged fetch is the upgrade path if the belief count ever gets large).

## `hello.role` for outbound routing — 2026-07-11
**What:** the `hello` handshake frame gained an optional `role:"ui"|"voice"` field (default `"ui"`). The Brain tracks each authenticated connection's role and gates both snapshot-push and broadcast frames through `_frame_visible_to(role, msg_type, payload)`.
**Why:** the contract's routing rule ("Voice is sent only its subset") was literally unimplementable without a client-identity signal at connect time — the snapshot fires before any `user_msg`, so nothing later in the stream could distinguish a UI client from a Voice client. Found and fixed after running the real stack (see Bugs.md); no automated test had asserted this until `test_mock.py`'s `check_voice_routing_subset` was added alongside the fix.
**Trade-off:** one more optional field on the most security-relevant frame in the contract; mitigated by defaulting unknown/absent role to `"ui"` (the permissive case), so no existing client (including raw test clients) silently loses data.

## Orb: free-placement drag, no edge-snap — 2026-07-12
**What:** `phase-1-plan.md`'s original Step 5 spec called for the orb to "snap to the nearest screen edge" on drag release. Reversed after user testing — the orb now stays exactly where it's dropped.
**Why:** direct user feedback ("I don't want it to stick to an edge like a magnet — I should be able to place it anywhere"). The plan doc itself was updated to match, so it stays an accurate record rather than describing removed behavior.
**Trade-off:** none functionally; `window-state` still persists whatever position the user leaves it at, so the "remembers position across restarts" acceptance criterion is unaffected.

## Orb is user-resizable, circle locked to `min(width,height)` — 2026-07-12
**What:** the orb window changed from fixed 64×64/`resizable:false` to `resizable:true`. The visible glass sphere is a child of a full-window "hit area," sized in JS (via `ResizeObserver` on `document.documentElement`) to `Math.floor(Math.min(width, height))` and centered by flexbox — so a non-square window never stretches the circle into an ellipse; the excess space on the longer axis just stays transparent. This part is unchanged and still holds.
**Why:** explicit user request after confirming the fixed-size orb worked correctly. The "always a circle, never an ellipse" constraint came from `advisor` review before implementation — the naive `width:100%;height:100%` approach would have shipped a visibly-broken ellipse on the very first non-corner drag.
**Superseded same day — the resize *mechanism*:** the original all-edge `RESIZE_HANDLE_PX`/`startResizeDragging` approach (see Gotchas.md) broke drag-to-move on the tiny orb and shipped as a real bug (see Bugs.md "Edge-based orb resize handle conflicted with drag-to-move"). Replaced with: resize confined to a single hover-revealed bottom-right corner grip (`RESIZE_CORNER_PX`), square-locked and clamped to `MIN_ORB_PX`–`MAX_ORB_PX` (48–128) via manual `setSize` in `onPointerMove`, with `tauri.conf.json`'s `maxWidth`/`maxHeight` set to match so the OS can't override the clamp either. Drag-to-move now unambiguously owns the rest of the surface.
**Trade-off:** the resize range is now bounded (48–128px) rather than unlimited — acceptable; an orb outside that range isn't a real use case, and the clamp is what prevents a stale/huge persisted `window-state` size from recurring visually even if the state file is ever corrupted again. `enforce_orb_size` (added, then removed same day — see Bugs.md) stays superseded: size is legitimately user-controlled within the clamp, not forced to a constant.

## Voice stack swap to local-first; SKILL.md format for generated artifacts — 2026-07-23
**What:** (1) **Voice STT/TTS moved on-device:** faster-whisper (SYSTRAN, MIT, CTranslate2 int8) replaces cloud Whisper; Kokoro (hexgrad, Apache-2.0, 82M params) replaces Deepgram Aura. Cloud versions stay as documented fallback if local unavailable. Piper explicitly excluded (upstream archived Oct 2025; GPL-3.0 relicense blocks public-repo use). Pipecat and openWakeWord unchanged. (2) **Skills and browser playbooks use SKILL.md format:** Anthropic Agent Skills standard (folder + YAML frontmatter + markdown + bundled scripts), open spec, ecosystem-adopted (VS Code, Codex, Gemini CLI, Goose by 2026). One portable format for both 3e-generated skills and 3b browser playbooks, making them shareable and version-controllable.
**Why:** (1) the PRD names local-first as a core principle; cloud STT/TTS contradicted it and cost recurring bills. faster-whisper+Kokoro run on CPU, keep audio device-local, and pip-install into the existing voice/ Python worker with no new dependencies. (2) SKILL.md is an open standard, not a library adoption — file-format decision only — and avoids inventing a new artifact shape for two different Phase-3 use cases. Portability matters: skills generated by Halo should be shareable outside Halo.
**Trade-off:** faster-whisper quality is comparable to Whisper-large but not identical (real-world variance ~1–2%); fallback to cloud Whisper is available. Kokoro has a smaller parameter budget than Aura but runs in real-time on CPU; fallback to cloud TTS if needed. SKILL.md stores metadata (name, description) at the top of the folder structure rather than as a separate manifest — folders are heavier than flat markdown files but the standard is worth the portability win.

## Document ingestion: extract-then-digest, no heavy deps — 2026-07-24
**What:** designed [systemdesign/13-document-ingestion.md](../systemdesign/13-document-ingestion.md) (+ techstack/13) after a live test showed 8 markdown files burning ~68k tokens and escalating to the HEAVY model. Three layers: (0) deterministic `extract.py` (extension→markdown dispatcher: pypdfium2/pypdf for PDF, mammoth DOCX, openpyxl XLSX, markdownify HTML) plus `file_read` cap 64KB→8KB with offset/limit paging; (1) projection-time eviction in `_prompt_messages` — tool results older than the current round become stable restorable stubs (file is still on disk = the reference); (2) `doc_digest` map-reduce tool — one LIGHT call per doc returning a fixed JSON digest, one reduce, only ~1–2k tokens ever enter chat history; digests cached by (path, sha256).
**Why:** the burn was verified quadratic — the tool loop re-sends full history every round, so each 64KB read is retransmitted on every later round; LIGHT failures on oversized prompts then escalate the bloated history to HEAVY. Researched via subagents against markitdown, docling, pymupdf4llm, unstructured, kreuzberg, OpenHands condenser, Anthropic context-editing/programmatic-tool-calling, Aider repo-map, LangGraph map-reduce, LlamaIndex DocumentSummaryIndex, LLMLingua; provenance table in the design doc.
**Trade-off:** rejected pymupdf4llm (AGPL — would drag the MIT-distributed repo into AGPL), docling (~1GB torch, CPU-slow; kept as optional future deep-parse tier), unstructured (Windows-hostile system binaries), LLMLingua (torch/GPU; degraded prompts hurt small models most). Layer-1 stubbing costs an occasional re-read round-trip when the model genuinely needs old content back — lossless because pagination exists. New deps are only mammoth/openpyxl/markdownify (pure Python, few MB).
